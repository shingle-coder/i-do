## 一、盘点范围与统计口径

### 1.1 排除规则

**目录排除**（目录名命中任一项，整棵子树跳过，不做逐文件判断）：

```
node_modules  .git  dist  build  coverage  .turbo  .next  out  .cache tmp  __pycache__  .venv  venv  target  .desktop-build  .dsh-build  lib
```

**扩展名排除**（文件扩展名命中任一项即跳过）：

```
.map  .tsbuildinfo  .pyc  .tgz  .log  .lock
```

规则之外的隐藏目录（`.agents`、`.github`、`.trae`、`.claude`、`.ssh`）不属于排除项，全部计入。

### 1.2 统计方式

- 枚举方式：`[System.IO.Directory]::EnumerateFiles` / `EnumerateDirectories` 配显式栈做深度优先遍历，目录入栈前判定排除规则，命中即剪枝，不进入子树；一次遍历产出全量清单并落盘，后续统计全部基于该清单，不重复扫盘。
- 文件数：统计实际文件，不含目录节点本身；字节数为文件长度（`FileInfo.Length`）之和。
- 行数：**仅文本文件统计**，二进制文件的行数留空。二进制判定为「扩展名黑名单 + 文件头 8192 字节内的 NUL 字节探测」双重判断；文本文件按 4 MB 分块解码后统计换行符个数，若末尾没有换行符则补 1。
- 目录统计：仓库共有 **2,947** 个目录节点（含各级子目录，不含被排除目录）。每个目录标注两个值——`直接`（本层文件数/字节）与递归值（含全部后代）。目录树中显示的是**递归值**。
- 单位：1 KB = 1024 B，1 MB = 1024 KB；百分比按四舍五入保留两位小数，合计可能存在 ±0.01% 的尾差。

## 十、目录树的展开规则

每棵目录树都**以该顶层目录为根**（而不是以仓库根为根）展开到第 5 层，因此对 `packages`、`snapshots`、`docs` 这类大目录的可见深度比「全仓一棵树」更深。节点后的数字是该目录的**递归值**，即含全部后代文件数与字节数。

### 10.1 超过 5 层的折叠

第 5 层仍有子目录的节点，行尾会标注 `（折叠 N 层子目录）`，表示此处折叠了 N 个子目录。本文档的目录树中共有 **21 处**折叠点：`packages` 15 处、`apps` 4 处、`snapshots` 2 处；`docs`、`scripts` 等较浅的树没有触发折叠。例如：

```
# packages 树中
|   |       |   \-- vfs-example/  14 个文件，263.5 KB   （折叠 14 层子目录）
```

折叠只影响版面，不影响数字：被折叠节点的文件数与字节数已经是递归汇总值。之所以要折叠，是因为仓库最深路径达 10 段，例如

```
packages/experimental/webworker-runtime/tests/fixtures/vfs-example/home/sessions/--dsh-workspace--/preview-showcase
```

这是 Web Worker 运行时测试用的「模拟工作区」夹具（`fixtures/vfs-example` 下伪造了一整套 `home/sessions/...` 与 `workspace/.agents/skills/...` 结构）。若全展开，仅 `packages` 一棵树就会超过 3,000 行。

## 十一、异常与需要注意的点

1. **`.ssh` 里有一个未加密的 PEM 私钥**（1 个文件，1,678 字节，以主机 IP 命名），不在排除规则内，已计入统计。本文档只记录其用途，不输出任何内容。仓库脚本没有引用它，建议确认是否应移出仓库或补入排除规则。这是本次盘点最需要人工确认的一项。

2. **`.claude` 只有一个 17 字节的指针文件**，内容指向 `../.agents/skills`，用于让 Claude 复用仓库共享技能目录。它和 `.ssh` 一样，都没出现在基线的顶层分布里，是基线口径的两处遗漏。

3. **`lib` 是否算源码产物，两套口径不一致**。基线计入、本次排除，导致 7,881 个文件的总量差异。本仓库的 `lib/` 是 TypeScript 编译输出，与 `dist/` 性质相同，因此本次按「构建产物」统一排除；如果要与基线对齐，把 `lib` 从排除规则里去掉即可复现 29,078。

4. **`.agents/notes` 单目录占全仓 19.3% 的文件数**（4,091 / 21,197），其中 `archived` 2,783 个（占该目录 68%）。若后续需要压缩盘点成本，这里是收益最高的剪枝点——`archived` 基本是历史存档，可按需排除。

5. **`packages/client` 与 `packages/experimental` 合计 5,873 个文件**，占 `packages` 的 51.6%。前者是 Web 客户端全部 UI 组件库（每个组件一个包，内部再分 `src/`、`tests/`、`locale/`），后者是实验特性集合。这两块是全仓阅读负担的主要来源。

6. **源码目录里混有二进制资产**。例如 `apps/web/tests/fixtures/office/preview.ppt`（592.5 KB）、`packages/client/ui-settings-account/src/client/assets/` 下的 6 张 `.webp` 引导图（单张最大 405.4 KB）、`docs/logo/logo.ico`（1.0 MB）。它们的行数列在清单中留空，这是刻意为之，不是漏统计。

7. **存在多处生成型超长文件，阅读时应按生成物对待**：`packages/extensions/tool-cordis/src/api-catalog.ts`（10,946 行 / 774.8 KB，由外部 API 目录生成）、`packages/extensions/cordis-client-runner/src/client/slot-catalog.ts`（5,782 行）、`packages/client/ui-*/src/client/locales.ts`（单文件 2,000–3,500 行的文案表）、`docs/persistence-catalog*.md`（各 9,400+ 行）与 `docs/config-catalog*.md`（各 5,300 行）。

8. **行数最多的 30 个源码文件里有 21 个与测试相关**（20 个 `*.spec.ts` / `*.e2e.ts`，另 1 个是 `tests/` 下的夹具模块）。这说明仓库的测试投入集中在少数超大端到端用例上（如 `agent-instructions.spec.ts` 6,586 行、`runtime.spec.ts` 5,862 行），单文件改动的连带风险较高。

## 十二、复现方式

全部数字由一份一次性枚举脚本产生，不重复扫盘。流程分三步：

1. **枚举**：从仓库根起做深度优先遍历，目录入栈前比对 17 个排除目录名，命中即剪枝；对生存的文件逐个读取 `FileInfo.Length`，再判定是否文本（扩展名黑名单 + 前 8192 字节 NUL 探测），文本按 4 MB 分块统计换行符，末尾无换行补 1。结果落为一张 TSV（相对路径、字节、行数、扩展名、一级目录、二级目录）。
2. **聚合**：遍历 TSV，把每个文件的计数向上累加到它的全部祖先目录，得到每个目录的直接值与递归值；再按一级目录、扩展名、体积、行数分别排序取 Top N。
3. **切块**：按「一级目录 / 二级目录」分组后贪心装箱，单块不超过 2,999 行数据 + 1 行表头，输出到 `docs/superpowers/inventory/`。

第 2、3 步的全部输入都来自第 1 步的 TSV，因此重跑统计不会重新读取源码文件。切块明细与各块的行数见 `docs/superpowers/inventory/00-index.md`。
